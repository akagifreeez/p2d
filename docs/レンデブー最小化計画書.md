# P2D レンデブー最小化計画書(シグナリングサーバー「最初だけ」化)

作成: 2026-09-13 / 状態: **計画(未着手)** — AI_SUMMARY「配送方式ロードマップ」の段階3.5
発動条件: 配信木計画(段階4)の着手が決まったとき、または「自前サーバーすら挟みたくないLAN運用」の要件が発生したとき
**推奨順序: 配信木(段階4)のM1より前に本計画を完了させる** — ツリーコーディネータがサーバーからホストへ移り、配信木のM1が半分消える

---

## 1. 目的と位置づけ

P2Dは既に8割P2Pである(チャット・発話状態・リモート操作・入力はDataChannel=端末直結)。
サーバーが今も通っているのは ①シグナリング(SDP/ICE) ②メンバー管理 ③リレー経路(Linux視聴者向け)
の3つ。本計画はこれを **「各参加者の最初の接続時だけサーバーを使い、以後は全員が全員と
相互に状態を交換する」** 構成に再編するもの。P2Dの「インフラゼロ」哲学の完全版。

引き換えに捨てるもの(合意済みの前提):
- **ハードNAT越えの保険**: サーバー経由リレーがなくなるため、直接繋がらないペアは繋がらない(TURN未設定時)。LAN用途は無影響
- **実装の複雑さ**: 名簿ゴシップのsplit-brain(同時参加の割れ)解決が難所

## 2. 目標アーキテクチャ

```
現状:   サーバー = シグナリング + 名簿 + リレー中継 + (将来)木コーディネータ
目標:   サーバー = 電話帳(ルームコード → 現メンバーの住所)   ← これだけ
        それ以外は全員がDataChannelで相互交換
LAN極限: QR/ディープリンクにホスト住所を埋めれば電話帳も不要(ホスト直行)
```

| 機能 | 現状 | 目標 |
|---|---|---|
| チャット・発話・リモ操作 | DC(既にP2P) | 変更なし |
| シグナリング(SDP/ICE) | サーバー経由 | 初回参加のみサーバー、**途中参加は既存メンバーのDC経由で中継** |
| メンバー名簿 | サーバーが権威 | **DCゴシップ**(全員が同一名簿を持つ・離脱はheartbeat検出) |
| リレー(Linux視聴者) | サーバーが中継 | **ホスト内蔵WSサーバー**に直結(サーバーはメディアに触れない) |
| 配信木コーディネータ(将来) | サーバーが権威(配信木計画書§3.3) | **ホストが権威**(根だから自然・木計画のM1が縮小) |

## 3. プロトコル設計(新規メッセージ)

### 3.1 名簿ゴシップ(DataChannel)

| メッセージ | 意味 |
|---|---|
| `roster:sync` | 自分の知る名簿全体(参加者ID・名前・参加時刻・能力)を送る。時刻の新しい方を採用する union 合流 |
| `roster:announce` | 「私が入った」(受信側は自分への接続を開始し、roster:syncを返す) |
| `roster:depart` | 「IDが抜けた」(heartbeat 5秒無応答でも発生。全員へ転送=ゴシップ) |

- **split-brain解決**: 同時参加で名簿が割れた場合、`joinedAt` + 参加者IDの辞書順で
  決定論的union。書き込み権威が存在しないため、衝突は「和集合+古い方のdepartを破棄」で収束させる。
- **中継シグナリング**: 途中参加者CがA経由で入る場合、C→(AのDC)→AがBへのofferを中継 →
  B↔Cが直接ICE。Aは単なる伝言板(既存のsignalingClientメッセージをDCにトンネルするだけ)。

### 3.2 ホスト内蔵マッチメーカー/リレー(Rust)

- ホストアプリがTCP+WSを **ローカルLANアドレスでlisten**(既存`relay:*`プロトコルをそのまま使用)。
- Linux視聴者はここへ直結 → シグナリングサーバーはメディア経路から完全撤退。
- ポートはroom:created時にシグナリングへ登録し、以後の参加者に配布。
- セキュリティ: リレー受付は参加コード保証付きハンドシェイク(接続時にroom code提示)のみ。

### 3.3 招待形式v2(サーバーなし参加)

```
p2d://join/<CODE>@<host>:<port>   … LAN直行(サーバー不使用)
p2d://join/<CODE>                  … 従来通り(シグナリングサーバーを電話帳として使用)
```
QRにも同梱。既存の `find_join_url` を拡張するだけ(Linux検証済みの実装があり低リスク)。

## 4. 信頼モデルとセキュリティ

- **信頼境界の移動**: リレー経路の信頼が「自前サーバー」→「参加者全員」へ寄る。
  したがって配信木計画書§3.5の **Ed25519署名(chunk完全性・真正性証明)を本計画でも必須コンポーネント**
  とする。ホストの鍵はroom:created時に生成し、`roster:sync` に公開鍵を同梱して配布する。
- シグナリングサーバーは「電話帳」であり、名簿の中身(改ざん後のstate)は個別接続の
  検証で最終的に担保される。電話帳が嘘の住所を出しても、接続先で署名検証が失敗するだけ。
- **不可避なサーバー残存要件**: ①インターネット越しのコード合流(電話帳が必要) ②ハードNAT用TURN
  (外部インフラ)。LAN運用では両方ゼロにできる。

## 5. マイルストーンと受け入れ基準

| 段階 | 内容 | 受け入れ基準 |
|---|---|---|
| M1 | 名簿ゴシップ(roster:sync/announce/depart)実装。サーバーはまだファンアウトも行う(二重化) | 実機E2E: 3台で(a)通常参加 (b)途中参加 (c)参加者のkill→全員の名簿が収束。split-brain(2台同時参加)の合流テスト |
| M2 | 途中参加のシグナリングをDC中継に切替。サーバー=電話帳専用化 | 実機E2E: **サーバーを参加後にkillしても新規参加が既存メンバー経由で成功**。既存1対1のE2Eにリグレッションなし |
| M3 | ホスト内蔵WSサーバー(リレー直結)。Ed25519署名(配信木§3.5)をリレー経路に導入 | 実機E2E: Linux視聴者がサーバーを一切経由せずホストからH264受信(pcapでサーバーへのメディア流量0を確認)。署名検証バッジ=緑 |
| M4 | 招待形式v2(住所埋め込み)+配信木コーディネータのホスト移管 | 実機E2E: LANでサーバープロセス停止状態でもQR参加→視聴→チャットが完結。配信木計画M2(固定2層木)がDC制御で成立 |

M1〜M2が名簿とシグナリング、M3がメディア経路、M4がLAN完全サーバーレス+配信木への接続。

## 6. 規模感とリスク

- **規模感**: リレー実装(済)と同程度〜やや上。M2(DC中継シグナリング)とM1(split-brain)が本体。
  配信木M1を半分消せるので、配信木までやるなら**総工数はむしろ減る**。
- リスク:
  1. **split-brainの境界ケース**: 同時参加・同時離脱・ Partition 復旧の組合せ。決定論的合流ルール
     (§3.1)を単体テストで網羅してから実機に進む。
  2. **接続率の低下**: TURN無し環境でハードNAT同士は繋がらない。UIには「中継不能」状態を明示し、
     必要ならTURN設定を促す(既存のTURN設定UIがある)。
  3. **旧クライアント混在**: roster同期はバージョン付きにし、v1クライアント混在時は従来のサーバー
     ファンアウトにフォールバック(M1の二重化を恒久フォールバックとして流用)。
  4. **ホスト内蔵サーバーの露出**: LAN listenはファイアウォール許可が必要(Windows初回プロンプト)。
     参加コードハンドシェイクなしの接続は拒否する。

## 7. 発動の判断基準

- **配信木(段階4)の着手を決めたら、まず本計画のM1〜M2を先にやる**(木のコーディネータが
  ホストに移り、木の実装がサーバー非依存になる)。
- LAN運用で「サーバープロセスすら立てたくない」需要が具体化したらM3〜M4。
- インターネット合流が主用途のうちは、電話帳としてのサーバーは残るため本計画の効果は部分的前後する —
  効果が最大化するのはLAN/自己完結ネットワーク運用。
