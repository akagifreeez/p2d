# P2D 配信木(オーバーレイマルチキャスト) 計画書

作成: 2026-09-13 / 状態: **計画(未着手)** — AI_SUMMARY「配送方式ロードマップ」の段階4
発動条件: 「同じ上り回線から多人数(目安5〜6人以上)へ配信するユースケース」が実際に発生したとき

---

## 1. 目的と位置づけ

現状のFull Mesh P2Pでは送信者の上り帯域が **視聴者数 × ビットレート** で線形増加する
(10人配信 = 上り30〜80Mbps + 10個のエンコーダ)。選択肢3(自前SFU)はこれを解決するが、
サーバーという固定インフラを要求する。

配信木は **視聴者自身が下流への再配信を担う** ことで、固定インフラなしのまま
送信者上りを fan-out数 k 倍(= 深さ log_k N で抑える)にする方式。
P2Dの「インフラゼロ」哲学を貫ったままスケールする唯一の選択肢であり、
その代償として **離脱耐性の実装**(最大の難所)と **画面内容が視聴者マシンを経由する**
という信頼モデルの変化を受け入れる。

```
Mesh(現状):      ホスト ══×N本══ 全員              ホスト上り = N × 2.5Mbps
配信木(本計画):  ホスト ──k本── A,B,C              ホスト上り = k × 2.5Mbps
                          A,B,Cが各k'本ずつ子へ      中継視聴者上り = k' × 2.5Mbps
```

## 2. 前提と既存資産(2026-09-13時点)

| 資産 | 配信木での使い道 |
|---|---|
| WSリレー `relay:h264`(H264/fMP4 boxストリーム) | **そのまま下流へパススルーできる**(再エンコード不要 = 品質劣化ゼロ・中継者のCPU負荷ほぼゼロ) |
| `relay:subscribe` / `relay:frame` / `relay:audio` | エッジ配信プロトコルの下位互換として残す |
| シグナリングサーバー(Node/WS) | メディアは通さず**ツリー割り当ての制御専用**に役割追加 |
| ピア再接続の実績コード | 離脱耐性の基礎(heartbeat・再参加フロー) |
| `relay:input`(リモート操作) | 親経由でホストへ中継するだけ |

重要: 本計画は既存WSリレーの**上に**乗る。H264パススルー方式のため
JPEG経路・WebRTC経路は一切変更しない。

## 3. 基本設計

### 3.1 トポロジ

- **根** = 配信ホスト。**内部ノード** = 子を引き受けた視聴者(sub-relay)。
- fan-out上限 k: ホストは4、中継視聴者は2(上り帯域の非対称性を考慮)を初期値とする。
- 深さ上限 D = 3(遅延の積み増しを ~300ms以内に収める)。
- 割り当ては **幅優先** (浅いノードから満たす)。深さを最小化するため。

### 3.2 輸送の選択: H264 chunkのパススルー

中継視聴者は受け取った `relay:h264` のbox列を **デコードせず** そのまま子へforwardする。
- 品質: 世代劣化なし(再エンコードしない)
- CPU: 中継者はデコードもエンコードも不要(受信中の再生タブとは別の軽量forwarder)
- 制約: 子は全員MSE対応エンジン必須(= JPEG専用視聴者は木に参加できない → その場合のみ親がJPEGにトランスコードするか、JPEG視聴者はホスト直接受信にフォールバック)

WebRTC転送(受信トラックを新PCに送る)は採用しない。理由: 中継者の再エンコードCPU・
ICE確立の手数・Linux視聴者が中継者になれない、の3点で劣る。

### 3.3 プロトコル(新規メッセージ。サーバーは制御のみ扱う)

| メッセージ | 方向 | 内容 |
|---|---|---|
| `tree:join` | 視聴者→サーバー | 参加申告(自身の上り帯域セルフ申告を含める) |
| `tree:assign` | サーバー→視聴者 | 親IDの割り当て(直接接続=host / 中継ノード=peerId) |
| `tree:promote` | サーバー→視聴者 | 中継ノードへの昇格(子を引き受ける指示) |
| `tree:parent_lost` | 視聴者→サーバー | 親の死の検出報告 → 再割り当て要求 |
| `tree:heartbeat` | 双方向 | エッジリンクの生存確認(既存relay:subscribeの拡張) |
| `tree:leave` | 双方向 | 正常離脱(子の再割り当てをトリガ) |

- シグナリングサーバーが **唯一のツリー状態保持者**(誰が誰の親か)。
  メディアバイトは一切通さないのでサーバー帯域コストは制御分のみ(= インフラゼロの帯域特性維持)。
- エッジのデータ経路は既存の `relay:*` を親子間でそのまま使う(メッセージ種別の追加なし)。

### 3.4 離脱耐性(最大の難所・工程の大半ここ)

1. **検出**: 子は親へのWS/エッジリンクでheartbeat。5秒無応答で `tree:parent_lost`。
2. **再割り当て**: サーバーは孤児を幅優先の空きスロットへ割り直す。目標切替時間 < 3秒。
3. **視聴の連続性**: 切替中は最終フレームを表示し続け(既存MSEバッファ)、新親のinit segmentから
   再append。GOP(約1秒)境界から復帰するため1〜2秒の画質欠落を許容。
4. **中継者の連鎖離脱**: 中継者が消えるとその子孫全員が孤立 → サーバーは subtree 単位で
   一括再割り当てする(個別にやると割り当ての二重掴みが起きる)。
5. **ホスト離脱**: ルーム終了(既存動作のまま)。

### 3.5 セキュリティ/プライバシー

- 画面内容が他視聴者のマシンを通ることを **参加者UIに明示** する(中継ノード名の表示)。
- 将来オプション: ルーム参加時に導出した共通鍵でH264 boxのペイロードをapplication-layer暗号化
  (パススルー互換のため box headerは素のまま、mdat内のみ暗号化)。MVPでは未実装。

## 4. マイルストーンと受け入れ基準

| 段階 | 内容 | 受け入れ基準 |
|---|---|---|
| M1 | サーバーにツリーコーディネータ(割り当てロジック+プロトコル)。UI変更なし | 単体テスト: 10ノードの割り当てシミュレーションで深さ≤3・fan-out≤上限を満たす |
| M2 | 固定2層木の手動構築(ホスト→中継1→子1) | 実機E2E: 子がH264を受信・描画(guest passed:true)、中継者でデコードが走っていないことをログで確認 |
| M3 | 自動割り当て+離脱耐性(中継者kill→子の自動再割り当て) | 実機E2E: 中継者kill後3秒以内に子が視聴再開。連鎖離脱(中継+その子を同時kill)でも復帰 |
| M4 | 視聴者数しきい値での自動モード切替(mesh ↔ tree)+設定UI | 実機E2E: 5人の疑似セッションで自動昇格/降格が切り替わる。既存1対1のE2Eにリグレッションなし |

各マイルストーン完了ごとにAI_SUMMARYの本計画へのリンク状態を更新する。

## 5. 規模感とリスク

- **規模感**: M1がサーバー中心で小さめ、M3(離脱耐性)が本体。合計でWSリレー実装(済)と同程度かやや上。
- リスク:
  1. **中継視聴者の上りが細い** → その枝だけfps/品質が下がる。セルフ申告帯域+実測(RTT)で
     fan-outを動的調整(M3以降)。解決ではなく分散であることは前부터合意済み。
  2. **NAT/ファイアウォール**: エッジがWS(TCP)なのでICE問題なし。ただし遅延がUDP比で増える。
  3. **複雑さの永久費**: 木の状態管理は一度入ると保守コストが残る。**使用実績が付くまでM1〜M4に
     着手しない**ことがこの計画自体の安全装置。

## 6. 発動の判断基準(将来の自分への引き継ぎ)
