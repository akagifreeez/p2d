## 1. 目的と位置づけ

現状のFull Mesh P2Pでは送信者の上り帯域が **視聴者数 × ビットレート** で線形増加する
(10人配信 = 上り30〜80Mbps + 10個のエンコーダ)。選択肢3(自前SFU)はこれを解決するが、
サーバーという固定インフラを要求する。

配信木は **視聴者自身が下流への再配信を担う** ことで、固定インフラなしのまま
送信者上りを fan-out数 k 倍(= 深さ log_k N で抑える)にする方式。
P2Dの「インフラゼロ」哲学を貫ったままスケールする唯一の選択肢であり、
その代償として **離脱耐性の実装**(最大の難所)と **画面内容が視聴者マシンを経由する**
という信頼モデルの変化を受け入れる。後者は **ホスト署名による完全性・真正性の証明(§3.5)**
で暗号学的に担保する — 中継ノードは鍵を持たない転送屋であり、受信者は受信した映像が
本物のホスト産であり未改変であることを検証できる。

```
Mesh(現状):      ホスト ══×N本══ 全員              ホスト上り = N × 2.5Mbps
配信木(本計画):  ホスト ──k本── A,B,C              ホスト上り = k × 2.5Mbps
                          A,B,Cが各k'本ずつ子へ      中継視聴者上り = k' × 2.5Mbps
```

## 2. 前提と既存資産(2026-09-13時点)

| 資産 | 配信木での使い道 |
|---|---|
| WSリレー `relay:h264`(H264/fMP4 boxストリーム) | **そのまま下流へパススルーできる**(再エンコード不要 = 品質劣化ゼロ・中継者のCPU負荷ほぼゼロ) |
| `relay:subscribe` / `relay:frame` / `relay:audio` | エッジ配信プロトコルの下位互換として残す |
| シグナリングサーバー(Node/WS) | メディアは通さず**ツリー割り当ての制御専用**に役割追加 |
| ピア再接続の実績コード | 離脱耐性の基礎(heartbeat・再参加フロー) |
| `relay:input`(リモート操作) | 親経由でホストへ中継するだけ |

重要: 本計画は既存WSリレーの**上に**乗る。H264パススルー方式のため
JPEG経路・WebRTC経路は一切変更しない。

## 3. 基本設計

### 3.1 トポロジ

- **根** = 配信ホスト。**内部ノード** = 子を引き受けた視聴者(sub-relay)。
- fan-out上限 k: ホストは4、中継視聴者は2(上り帯域の非対称性を考慮)を初期値とする。
- 深さ上限 D = 3(遅延の積み増しを ~300ms以内に収める)。
- 割り当ては **幅優先** (浅いノードから満たす)。深さを最小化するため。

### 3.2 輸送の選択: H264 chunkのパススルー

中継視聴者は受け取った `relay:h264` のbox列を **デコードせず** そのまま子へforwardする。
- 品質: 世代劣化なし(再エンコードしない)
- CPU: 中継者はデコードもエンコードも不要(受信中の再生タブとは別の軽量forwarder)
- 制約: 子は全員MSE対応エンジン必須(= JPEG専用視聴者は木に参加できない → その場合のみ親がJPEGにトランスコードするか、JPEG視聴者はホスト直接受信にフォールバック)

WebRTC転送(受信トラックを新PCに送る)は採用しない。理由: 中継者の再エンコードCPU・
ICE確立の手数・Linux視聴者が中継者になれない、の3点で劣る。

### 3.3 プロトコル(新規メッセージ。サーバーは制御のみ扱う)

| メッセージ | 方向 | 内容 |
|---|---|---|
| `tree:join` | 視聴者→サーバー | 参加申告(自身の上り帯域セルフ申告を含める) |
| `tree:assign` | サーバー→視聴者 | 親IDの割り当て(直接接続=host / 中継ノード=peerId) |
| `tree:promote` | サーバー→視聴者 | 中継ノードへの昇格(子を引き受ける指示) |
| `tree:parent_lost` | 視聴者→サーバー | 親の死の検出報告 → 再割り当て要求 |
| `tree:heartbeat` | 双方向 | エッジリンクの生存確認(既存relay:subscribeの拡張) |
| `tree:leave` | 双方向 | 正常離脱(子の再割り当てをトリガ) |

- シグナリングサーバーが **唯一のツリー状態保持者**(誰が誰の親か)。
  メディアバイトは一切通さないのでサーバー帯域コストは制御分のみ(= インフラゼロの帯域特性維持)。
- エッジのデータ経路は既存の `relay:*` を親子間でそのまま使う(メッセージ種別の追加なし)。

### 3.4 離脱耐性(最大の難所・工程の大半ここ)

1. **検出**: 子は親へのWS/エッジリンクでheartbeat。5秒無応答で `tree:parent_lost`。
2. **再割り当て**: サーバーは孤児を幅優先の空きスロットへ割り直す。目標切替時間 < 3秒。
3. **視聴の連続性**: 切替中は最終フレームを表示し続け(既存MSEバッファ)、新親のinit segmentから
   再append。GOP(約1秒)境界から復帰するため1〜2秒の画質欠落を許容。
4. **中継者の連鎖離脱**: 中継者が消えるとその子孫全員が孤立 → サーバーは subtree 単位で
   一括再割り当てする(個別にやると割り当ての二重掴みが起きる)。
5. **ホスト離脱**: ルーム終了(既存動作のまま)。

### 3.5 データ完全性と真正性の証明(本計画の中核要件)

木構造では画面内容が**他視聴者のマシン**を経由する。中継ノードは改ざん・差し替え・
注入が技術的に可能なので、受信者は「この映像は本物のホストが作った、改変されていない」
を暗号学的に検証できなければならない。グループ共通鍵のHMACでは**悪意ある中継者自身が
鍵を知っている**ため防御にならず、**非対称署名(ホストだけが署名できる)**を採用する。

#### 脅威モデル

| 攻撃者 | 可能な行為 | 対策 |
|---|---|---|
| 悪意ある中継ノード | chunkの改ざん・差し替え・注入・リプレイ | 署名検証で検知→破棄+UI警告 |
| 悪意ある中継ノード | 選択的破棄(通過を止める) | 暗号では防げない(可用性攻撃)。seq gap検出で表示+自動再割り当て(M3) |
| 信号路上の第三者 | 盗聴・改ざん | シグナリングはWSS/TLS。エッジは署名で真正性確保(機密性は将来のペイロード暗号化) |
| 偽ホスト | ルーム自体のなりすまし | シグナリングサーバーのroom状態が信頼境界(現状と同一)。強化はQRに鍵フィンガープリント同梱で帯域外検証 |

#### 署名スキーム(Ed25519 / tweetnacl)

- ホストは**ルーム作成時にセッション用Ed25519鍵対を生成**(永続化しない。ルーム単位で使い捨て)。
- 公開鍵は `relay:key` メッセージで視聴者に配布(シグナリングWS/TLS経由。信頼境界は既存の
  room membershipと同一)。より強くやるならQRコードに鍵のフィンガープリントを同梱し、
  スキャンした端末と帯域外で突合できるようにする。
- 各 `relay:h264` / `relay:audio` chunkは `{v, seq, ts, d, sig}` 構造に拡張し、
  `sig = Ed25519.sign(host_sk, hash(seq ‖ ts ‖ d))` を付与。
  - seqを署名対象に含めることで**リプレイ・並べ替え攻撃**も検出(受信者は送信者ごとの最大seqを追跡)。
  - 鍵配布のブートストラップ: 初回は `relay:key` を待ってから検証開始。それ以前のchunkは破棄しないが「未検証」として表示。
- **中継ノードは署名を再付与できない**(秘密鍵はホストのみ)。中継は `(chunk, sig)` の
  不透明ペアをforwardするだけ = 「鍵を持たない転送屋」。改ざん・再署名は受信側の検証で必ず弾ける。
- 実装は **tweetnacl**(純JS・依存ゼロ・~30KB)を使う。WebCryptoのEd25519はエンジン差が
  大きいため、WebKitGTKでも確実に動く純JSを選択。コスト: 署名~1ms/検証~1ms × 1〜5chunk/s =
  ホスト・受信者とも誤差レベル。転送オーバーヘッドは signature 64B + base64膨張 ≈ chunkあたり+90B(chunk 50〜200KBに対し<0.2%)。

#### 動作ポリシー

- 署名検証: **リレーモードではデフォルトON**(コストが無視できるため)。失敗chunkは破棄し、
  タイルに「改ざん検出」警告を表示。連続失敗で当該親からの受信を停止し `tree:parent_lost` 相当の再割り当てへ。
- 検証状態はタイルバッジで可視化: 検証済み(緑) / 未検証・旧クライアント(灰) / 改ざん検出(赤)。
- メッシュ(WebRTC)経路はDTLS-SRTPが端末間の完全性を既に保証するため署名なし(対象外)。

#### 制御面との関係

`tree:assign` 等の制御メッセージはシグナリングサーバー(TLS)が信頼境界。仮に割り当てを
悪用して悪意ある親へ誘導されても、**メディアの署名検証が独立に成立している**ため
偽映像の注入は不可能(可用性は落ちるが完全性は保たれる)。信頼の根を制御面と分離するのが意図。

## 4. マイルストーンと受け入れ基準

| 段階 | 内容 | 受け入れ基準 |
|---|---|---|
| M1 | サーバーにツリーコーディネータ(割り当てロジック+プロトコル)。**chunk署名エンベロープの設計確定**(後付けは破壊的変更になるためM1で固定) | 単体テスト: 10ノードの割り当てシミュレーションで深さ≤3・fan-out≤上限を満たす。署名フォーマットのシリアライズ/検証単体テスト |
| M2 | 固定2層木の手動構築(ホスト→中継1→子1)+ **ゲスト側署名検証の実装**(tweetnacl) | 実機E2E: 子がH264を受信・描画し署名検証バッジ=緑。中継者でデコードが走っていないことをログで確認 |
| M3 | 自動割り当て+離脱耐性(中継者kill→子の自動再割り当て)+ **改ざん検出テスト** | 実機E2E: 中継者kill後3秒以内に子が視聴再開。**中継者がchunkを改ざんすると子が検出・破棄・警告表示する**(攻撃シミュレーションをテストコードで実施)。連鎖離脱でも復帰 |
| M4 | 視聴者数しきい値での自動モード切替(mesh ↔ tree)+設定UI+QRへの鍵フィンガープリント同梱 | 実機E2E: 5人の疑似セッションで自動昇格/降格が切り替わる。既存1対1のE2Eにリグレッションなし。QRにフンガープリントが表示され帯域外照合できる |

各マイルストーン完了ごとにAI_SUMMARYの本計画へのリンク状態を更新する。

## 5. 規模感とリスク

- **規模感**: M1がサーバー中心で小さめ、M3(離脱耐性)が本体。署名はtweetnacl(純JS・依存ゼロ)で
  M2に一段落。合計でWSリレー実装(済)と同程度かやや上。
- リスク:
  1. **中継視聴者の上りが細い** → その枝だけfps/品質が下がる。セルフ申告帯域+実測(RTT)で
     fan-outを動的調整(M3以降)。解決ではなく分散であることは前から合意済み。
  2. **NAT/ファイアウォール**: エッジがWS(TCP)なのでICE問題なし。ただし遅延がUDP比で増える。
  3. **複雑さの永久費**: 木の状態管理は一度入ると保守コストが残る。**使用実績が付くまでM1〜M4に
     着手しない**ことがこの計画自体の安全装置。
  4. **機密性は範囲外**: 本計画の署名は完全性・真正性のみ。盗聴対策(ペイロード暗号化)は
     別途(§3.5の将来オプション)。暗号化+署名を同時にやるとパススルー互換の設計が複雑化するため
     分離してある。

## 7. M5: リアルタイム回復・UX(2026-09-14 追加、フェーズA着手)

### 7.1 問題定義(ユーザビリティ)

現状の「切替」の発火条件は**死(接続断)のみ**。親が生きているが遅い(帯域細い・
エンコード停滞)場合、子は固まり続け、状態も見えない。ユーザーに約束すること:

1. 固まりを検知したら数秒で自動回復する(ユーザー操作不要)
2. 固まっている間、「復旧中」が見える(フェーズBでUI化)
3. 勝手にフラップしない(単発欠落で切替えない)

### 7.2 設計: 劣化3段階

| レベル | 状態 | 検知 | 動作 | 見える化(フェーズB) |
|---|---|---|---|---|
| L0 | 正常 | — | — | 緑 |
| L1 | 品質低下 | seq欠落率・RTT (計測はフェーズC) | 切替しない | 黄 |
| L2 | 停滞 | ウォッチドッグ: アクティビティ(メディア or tick)が4秒無音 | `tree:parent_lost` 送信 → ホストが再割当 → 別の親へ | 赤+再接続中 |
| L3 | 完全切断 | WS close | 既存の移行経路(§M2の4秒+バックオフ) | 赤+再接続中 |

フラップ防止: 切替後30秒のクールダウン。再割当が12秒来なければ同一親への
強制再接続(フォールバック)。単発欠落では発動しない(L2のしきい値は連続無音)。

### 7.3 tickと親lostの経路

- ホストは共有中、全リレー購読者へ1秒毎に `relay:tick` を送る。共有停止時は
  `relay:share_state {active:false}` を送って視聴者の監視を解除する
  (静止画で送信量が減る正常系と、リンク停滞を区別するため)
- 中継は tick/share_state を下流へパススルー (無署名の制御メッセージ)
- 視聴者の監視対象は「tick と メディア のどちらか新しい方」。両方4秒無音でL2発動
- L2で親へ `tree:parent_lost` を送る (中継経由の場合は中継が originId を付けて
  ホストへ転送)。ホストは該当視聴者を木から外して再割り当てする。
  root直結へ戻す場合も `tree:assign {addr: ホストaddr}` で明示的に付け替える
  (停滞した親のサーバーに繋がったまま残らないように)

### 7.4 フェーズと決定事項(2026-09-14 本人決定)

- **フェーズA (着手)**: ウォッチドッグ+parent_lost送信+再割当+クールダウン。
  切替判定は純粋ロジック (`src/lib/relayWatchdog.ts`) に分離して単体テスト
- **フェーズB (実装済み 2026-09-14)**: 見える化。タイルバッジ (緑=直結/中継経由・
  黄=不安定・赤=再接続中)、回復/不安定トースト。**mesh/配信木でUI共通化**、検知だけ
  経路別に分岐 (meshは既存connectionQualityをバッジへマッピング)
- **フェーズC (実装済み 2026-09-14、一部)**: 中継→ホストの5秒周期メトリクス
  (tree:metrics: 子数・上流無音時間) を記録し、**不健康な中継への新規割当を回避**
  (pickParent に skip フィルタ)。※既存の子の引き剥がし(降格)と実測RTTスコア化は未着手
